## 1. Schema Overview

- **Database:** Neon serverless Postgres (Launch plan at launch; Scale plan when sustained load or retention needs grow; one project with branches for preview/staging) -- technical-architecture.md Section 3, ADR-003.
- **ORM:** Drizzle ORM v1 with drizzle-kit migrations, Neon serverless driver in WebSocket/Pool mode so interactive transactions (`SELECT ... FOR UPDATE`) work from Vercel functions and Trigger.dev tasks -- Section 3, ADR-004.
- **Tables:** 49 (45 domain entities + 1 junction table + 3 lookup tables). The 45 entity tables are the 23 Stage 3 entities (21 from Shared Data Entities plus Accounting Export File and Data Export Archive, per technical-profile.md Section 5) and 22 implicit entities discovered from the specs and the architecture (Step 1 sweep, tagged in each table's Source line).
- **Relationships:** 101 (88 one-to-many, 1 many-to-many, 12 one-to-one). Each FK is one relationship; the many-to-many relationship is counted once although its junction table carries two FKs.
- **Migration strategy:** migration-based, consistent with technical-architecture.md Section 6 and ADR-020: every change is generated by `drizzle-kit generate` as a reviewed, committed SQL file and applied by `drizzle-kit migrate` in CI to preview branches, staging and production. Constructs Drizzle's schema DSL cannot express (row-level security policies, immutability triggers, partial and expression indexes, `tsvector` generated columns, cross-column CHECKs, the two-phase deletion helpers) are hand-authored as custom migration files in the same reviewed chain.

### Entity Map

**Domain Entities (Stage 3 -- 23):**
- freelancer_account -> belongs to user; has one branding_profile, subscription_plan, payment_account_connection, custom_domain, referral_attribution, storage_usage, invoice_counter; has many client, notification, support_access_session, data_export_archive, accounting_export_file, activity_log_entry, financial_totals (and is the tenant key on every owned table)
- client -> belongs to freelancer_account; has many client_contact, project
- client_contact -> belongs to client; actor on proposal acceptance, milestone approval, comment, payment; has many portal_token, portal_session
- project -> belongs to client; has many proposal, milestone, invoice; has one payment_schedule
- proposal -> belongs to project; has one proposal_signature; references payment_schedule; has many comment (change requests), proposal_resend_event
- payment_schedule -> belongs to project (one per project); has many payment_schedule_change
- milestone -> belongs to project; has many deliverable, comment; may trigger many invoice
- deliverable -> belongs to milestone; has many deliverable_version, upload_session
- deliverable_version -> belongs to deliverable; anchors many comment
- comment -> pinned to exactly one of deliverable_version, milestone, proposal; may reply to comment
- invoice -> belongs to project; has one invoice_snapshot; has many payment, reminder_log; addressed to many client_contact; may correct an invoice
- payment -> belongs to invoice
- reminder_log -> belongs to invoice; links the notification it sent
- activity_log_entry -> belongs to freelancer_account and usually project; has one activity_log_entry_subject
- notification -> belongs to freelancer_account; references notification_type, project and the recipient
- branding_profile, subscription_plan, payment_account_connection, custom_domain, referral_attribution -> each belongs to one freelancer_account
- support_access_session -> belongs to freelancer_account; opened by an operator user
- accounting_export_file, data_export_archive -> belong to freelancer_account

**Domain Entities (Implicit -- 22):** user, auth_account, auth_session, auth_verification, email_change_request, auth_rate_limit (identity/session, Section 11); portal_token, portal_session (portal realm, Section 11); proposal_signature (FEAT-26), proposal_resend_event (FEAT-02.SPEC-007), payment_schedule_change (FEAT-04 change_history), invoice_snapshot (FEAT-09.SPEC-007), activity_log_entry_subject (FEAT-13.SPEC-004), notification_preference (FEAT-21.SPEC-008), help_tip_dismissal (FEAT-30), feed_item_read_state (FEAT-29.SPEC-003), storage_usage (FEAT-16.SPEC-005), financial_totals (FEAT-12.SPEC-004, ADR-013), upload_session (FEAT-16.SPEC-002, ADR-008), invoice_counter (FEAT-09.SPEC-007, ADR-014), inbound_event (ADR-023), job_outbox (ADR-012).

**Junction Tables:**
- client_contact_invoice -> connects client_contact <-> invoice (Invoice "addressed to the client's Primary contact(s)", feature-dependency-map.md Invoice relationships)

**Lookup Tables:**
- invoice_status -> referenced by invoice (10 values, more than 8)
- notification_type -> referenced by notification, notification_preference (29 registered types)
- activity_event_type -> referenced by activity_log_entry (closed vocabulary plus extensions, more than 8 values)

## 2. Table Definitions

Conventions that apply to every table below and are not repeated in Notes cells: `id` is `uuid` PK default `gen_random_uuid()`; `created_at` and `updated_at` are `timestamptz NOT NULL DEFAULT now()` (`updated_at` is refreshed on every write by the ORM `$onUpdate` hook or a trigger; on append-only tables it simply never changes after insert). Every `freelancer_account_id` column is the tenant key (Section 4). "FK idx" means an index on the FK column; where a UNIQUE or composite index already leads with the FK column it is the FK index. Nullable FK columns use partial indexes (`WHERE col IS NOT NULL`). Enum type names are defined in Section 8. Monetary columns end in `_minor` and hold integer minor units in `numeric(20,0)`.

| inbound_event, job_outbox | No -- operational ledgers | No -- system-written | No -- unique event id and dedupe key provide exactly-once (ADR-023, ADR-012) | inbound_event purged 90 days after `processed_at`, job_outbox 30 days after `acknowledged_at` (both Assumptions -- no spec sets a window; payloads may hold GDPR-class data, Section 5) |

**Multi-tenancy:** Multi-tenant, shared schema with the Freelancer Account as the tenant. Every account-owned table carries `freelancer_account_id` as the tenant key (NOT NULL, FK to freelancer_account, ON DELETE CASCADE except the retention-capable tables invoice, payment and activity_log_entry, which detach and carry `retention_hold_at`), and every Section 5 policy scopes by it. Evidence: BRIEF.md Privacy ("strict isolation between clients") and ASMP-23 ("a client never sees another client's anything"); feature-dependency-map.md Freelancer Account "Owns every Client, Project, Branding Profile, Subscription Plan, Payment Account Connection, Referral Attribution, and Activity Log Entry"; Sec 11 "every query scoped by `freelancer_account_id`". No organization or team level exists above the account, so the tenant column is `freelancer_account_id` itself rather than a separate `tenant_id`: solo freelancers only (SC-01, cited in FEAT-01 Non-Goals), and a separate `tenant_id` would duplicate the same value. Schema-per-tenant and database-per-tenant are rejected because a few thousand tenants (ASMP-22) would multiply migrations across Neon branches (ADR-020) for no isolation benefit that row-level security does not already give. Tables scoped only through a parent (invoice_snapshot, activity_log_entry_subject, client_contact_invoice, and the auth tables) are protected by policies joining to the tenant-keyed parent.

## 5. Security & Access Model

**Enforcement model:** Row-level security (RLS) -- Neon Postgres supports it, so RLS is the primary authorization mechanism at the data layer, with `FORCE ROW LEVEL SECURITY` on every table and the application guard (`defineAction` / `defineQuery`, Section 10) as the first, defense-in-depth layer computing the same predicates. Interactive transactions on the Neon Pool driver (Section 3, ADR-004) let each request run `SET LOCAL app.realm = ..., app.freelancer_account_id = ..., app.client_id = ..., app.client_contact_id = ..., app.portal_role = ..., app.support_freelancer_account_id = ...` before its queries, so the settings cannot leak across pooled connections. Roles are exactly the four Section 11 roles (Nadia = `freelancer`, Owen = portal `primary`, Priya = portal `reviewer`, Dana = `operator`); the database principals used to run them are `app_runtime` (no BYPASSRLS), `app_operator_ro` (SELECT-only grants, the read-only connection Section 10 already requires for operator reads) and `app_system` (webhook processors, Trigger.dev tasks and sweeps, realm `system`, scoped per task by `app.freelancer_account_id` except the named cross-account sweeps). These principals are infrastructure, not additional product roles.

### Growth-Tier Notes

- **Partition `activity_log_entry` (and `inbound_event`) by month on `occurred_at` / `received_at`:** trigger when either exceeds tens of millions of rows or trail queries drift past the ~2 s interactivity target (ASMP-21); requires the immutability trigger and retention-hold purge to be partition-aware.
- **Read replica (Neon read replica) for the operator read-only connection and dashboard reads:** trigger when support-session reads or FEAT-12 aggregation contend with write latency on invoice payment flows.
- **Materialized read model for portal home or roster stage (Section 6 candidates):** trigger when the measured p95 of those joins exceeds the mobile target of roughly 2 seconds (ASMP-21).
- **Object-storage tiering or archival for old deliverable versions:** trigger when stored bytes threaten the roughly $100/month budget (architecture Section 2: ~20 TB could cost ~$300/month); the schema already tracks bytes in `storage_usage` and `deliverable_version.size_bytes`.
- **Increase Neon compute or move to the Scale plan:** trigger when sustained load or point-in-time-restore retention needs exceed the Launch plan (Section 3 database recommendation).

## 9. Anti-Pattern Validation

| # | Check | Result | Notes |
|---|-------|--------|-------|
| 1 | Every table has a primary key | PASS | 48 tables have `id uuid` PK; the one junction table client_contact_invoice has the composite PK (client_contact_id, invoice_id) as the guide prescribes for pure junctions |
| 2 | Every relationship has a FK constraint | PASS | All 101 relationships in Section 3 are declared FKs with explicit ON DELETE and ON UPDATE CASCADE. Opaque identifiers that are not internal relationships (`notification.dedupe_key`, `inbound_event.subject_ref`, provider references such as `processor_payment_ref`) are external keys, not associations |
| 3 | Column types match data semantics | PASS | UUID for identifiers, timestamptz for instants, date for calendar dates, boolean for flags, jsonb for flexible payloads, inet for addresses, char(3) ISO 4217 codes, bounded varchar for names and text for long content; non-obvious mappings are documented in Notes cells (bigint byte counts, numeric(7,4) tax rates) |
| 4 | Monetary values use DECIMAL (not INTEGER/FLOAT) | PASS | Every `_minor` column is `numeric(20,0)` (an exact DECIMAL of scale 0). Reconciliation with ADR-016/ADR-028 ("integer minor units + ISO 4217", branded MinorUnits type): the stored value is the integer minor-unit count so zero- and three-decimal currencies stay exact, while the column type is DECIMAL so the guide's exact-decimal rule holds; the Drizzle mapping converts to the application's bigint/MinorUnits type at the boundary. Tax rates are numeric(7,4) |
| 5 | No comma-separated value columns | PASS | Plural fields are tables (notification_preference, help_tip_dismissal, payment_schedule_change, auth_session, client_contact_invoice); the only multi-value columns are jsonb documents (`part_etags`, `snapshot`, `payload`, `detail`) holding structured provider or event data, not delimited strings |
| 6 | FK columns are indexed | PASS | Every FK column has an index listed in its table's Indexes block (leading column of a composite or unique index where noted, partial indexes for nullable FKs); read-pattern indexes are additional |
| 7 | Timestamps include timezone | PASS | Every timestamp column is `timestamptz`; the date-only columns (`issue_date`, `due_date`, `target_date`, `sent_local_date`, `date_range_*`) are calendar dates by specification, and time-zone semantics for them come from freelancer_account.time_zone (FEAT-15.SPEC-006) |
| 8 | No unconstrained polymorphic associations | PASS | No `*_type` + `*_id` pairs. Comment target, activity subject, feed item source and notification recipient use exclusive nullable FKs with CHECKs; `activity_log_entry_subject.subject_kind` is an enum snapshot paired with real FKs, not a generic id |
| 9 | No god tables (>20 columns) | PASS | Widest tables: proposal 19, payment 19, invoice 19, freelancer_account 17, notification 16, milestone 16; wide candidates were split (invoice_snapshot, proposal_signature, activity_log_entry_subject) |
