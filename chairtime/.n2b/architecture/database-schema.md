# Database Schema Design -- Chairtime

## 1. Schema Overview

- **Database:** Supabase Postgres (Pro tier, US East region), used as standard Postgres 15+ with the `btree_gist` extension for exclusion constraints and row-level security as defense-in-depth for per-Pro isolation (technical-architecture.md Section 3, ADR-003).
- **ORM:** Drizzle ORM (with drizzle-kit migrations) over the `postgres` (postgres.js) driver through Supabase's connection pooler, transaction mode (technical-architecture.md Section 3, ADR-004).
- **Tables:** 41 (38 domain entities + 0 junction tables + 3 lookup tables). The 38 entity tables are the 18 Stage 3 Shared Data Entities, the 4 identity/session tables from technical-architecture.md Section 11 (`user`, `session`, `verification`, `support_session`), the Slot Hold entity named in the FEAT-03 Entity-Lifecycle Coverage Matrix, and 15 implicit entities tagged with their source in Section 2. No true many-to-many relationship exists in the Stage 3 relationship prose (every "has many" is answered by a "belongs to one"), so no junction table is created.
- **Relationships:** 68 foreign-key relationships (60 one-to-many, 8 one-to-one, 0 many-to-many). Stage 3's 56 named entity-to-entity relationships (technical-profile Section 2) are a count of prose mentions in both directions; the 68 here count physical FK constraints, including the tenant key (`pro_account_id`) on every Pro-owned table, the lookup FKs, and the implicit-entity FKs.
- **Migration strategy:** Migration-based, consistent with technical-architecture.md Section 6 and ADR-019: every change is generated by `drizzle-kit generate` into reviewed, checked-in SQL files, hand-edited where Drizzle cannot express the object (the `btree_gist` extension, exclusion constraints, RLS policies, the append-only grants on `activity_event`, the read-only support role and masked views, partial indexes), and applied by `drizzle-kit migrate` in CI to staging then production. Never `push` against shared environments.

**Conventions used throughout.** Table names are singular snake_case to match technical-architecture.md Section 11 (`user`, `session`, `pro_account`, `access_link`, `support_session`) and the Better Auth conventions; FK columns are named `{table}_id`. Postgres type mapping (reference dialect of schema-design-guide.md): short text `VARCHAR(n)`, long text `TEXT`, money `DECIMAL(10,2)`, percentage `DECIMAL(5,2)`, timestamps `TIMESTAMPTZ`, flexible structure `JSONB`, identifiers `UUID DEFAULT gen_random_uuid()`, ISO currency `CHAR(3)`, ISO country `CHAR(2)`, phone numbers E.164 `VARCHAR(16)`. Enumerations with fewer than 8 stable values and no metadata are `VARCHAR` with a `CHECK (col IN (...))`; enumerations with 8 or more values, or with metadata, are lookup tables (Section 8). Non-obvious mappings are called out in each Notes cell. Every domain table carries `id`, `created_at`, `updated_at`; the Section 4 decisions add `deleted_at` and `version` only where evidence activates them.

**Design notes that shape the whole schema.**

1. **Tenant key.** Every Pro-owned table carries `pro_account_id` (NOT NULL unless noted) so row-level security can scope every row directly, as technical-architecture.md Section 10 ("Tenant scoping") and Section 11 require. The Pro Account row is never deleted: account closure de-identifies it and hard-deletes its personal children (FEAT-29.SPEC-008 / SPEC-013, XBR-20, SC-22), so every FK to `pro_account` is `ON DELETE RESTRICT`.
2. **Slot non-overlap is enforced by the database** (ASMP-26; feasibility FEAT-03 Hard). `booking.occupied_range` (a `TSTZRANGE` covering appointment plus buffer) carries a partial `EXCLUDE USING gist` constraint over the slot-occupying states. A slot hold is not a second occupancy record: FEAT-03 states that a checkout hold and a Pro-created deposit-request hold are each owned by a Pending Payment booking, so the hold is a `slot_hold` row (expiry and state) attached to that booking, and the exclusion constraint on the booking is what makes a hold exclusive. Postgres exclusion constraints cannot span tables, so Time Blocks (which the specs allow to overlap a confirmed booking by the Pro's explicit "keep as exception" choice, XBR-11) and calendar busy time are checked inside the booking-commit transaction (row lock on the Pro Account row, then re-validation), not by a constraint.
3. **Financial records are never deleted** (SC-22, XBR-07). Money columns are `DECIMAL(10,2)`; Chairtime's own fee is always zero (XBR-07), so no platform-fee column exists; only the processor's card fee is stored.
4. **Calendar events are not stored** (FEAT-04.SPEC-005 Data Model: calendar events "not persisted as a Chairtime entity"). If the calendar provider cannot re-find an event it wrote without an identifier, the implementing team must add a correlation column to the booking side; this is flagged, not designed, here.
5. **Section 11 field reconciliation.** Section 11 lists `stripe_connected_account_id` and `stripe_customer_id` on `pro_account`; this schema places them where Stage 3 ownership puts them (`payout_account.processor_account_reference`, `subscription.processor_customer_ref`) so each fact has one home (3NF, Section 6). Section 11's `pro_account.status` value set (`setup`, `live`, `paused`, `system_paused`, `closing`, `closed`) is kept; it maps to Stage 3's Active | Paused | Closing | Closed with `setup` (pre-go-live, FEAT-15) and `system_paused` (subscription-lapse pause, FEAT-18.SPEC-004) as the refinements the specs require.

### Entity Map

**Domain Entities (Stage 3 Shared Data Entities):**
- pro_account -> has many service, availability_rule, time_block, calendar_connection, client, booking, cancellation_policy; has one subscription, payout_account; belongs to user (1:1, nullable after closure)
- service -> belongs to pro_account; referenced by booking, waitlist_entry, recurring_series
- availability_rule -> belongs to pro_account; has many availability_window
- time_block -> belongs to pro_account; optionally belongs to time_block_recurrence
- calendar_connection -> belongs to pro_account; has many calendar_busy_period
- client -> belongs to pro_account; has many booking, messaging_consent, access_link, waitlist_entry, recurring_series
- booking -> belongs to pro_account, client, service, cancellation_policy; optionally recurring_series; has one deposit_transaction, zero or one balance_payment, zero or one booking_termination, zero or one slot_hold; has many message, activity_event, payment_attempt
- deposit_transaction -> belongs to booking
- cancellation_policy -> belongs to pro_account; referenced by booking
- messaging_consent -> belongs to client (nullable after client deletion)
- message -> belongs to booking (or to pro_account for Pro notifications)
- subscription -> belongs to pro_account (1:1)
- waitlist_entry -> belongs to client, service; may convert into a booking
- recurring_series -> belongs to client, service; has many booking
- payout_account -> belongs to pro_account (1:1); has many payout
- activity_event -> belongs to booking or to pro_account (support-view log)
- access_link -> belongs to client; optionally booking
- balance_payment -> belongs to booking (0..1)

**Identity and Access Entities (technical-architecture.md Section 11):**
- user -> has many session; has one pro_account (role `pro`); has many support_session as operator (role `support`)
- session -> belongs to user
- verification -> standalone one-time-code store keyed by contact identifier (deliberately no FK, see the verification table)
- support_session -> belongs to user (operator), pro_account; optionally help_request

**Implicit Entities (discovered in Step 1, each tagged with its source in Section 2):**
- slot_hold, availability_window, time_block_recurrence, calendar_busy_period, booking_termination, booking_link_forward, setup_step_progress, help_request, data_export, attention_item, payout, payment_attempt, webhook_event, outbox_event, insights_daily_aggregate, insights_daily_service_tally

**Junction Tables:**
- None (no many-to-many relationship in the Stage 3 relationship prose).

**Lookup Tables:**
- booking_state -> referenced by booking
- activity_event_type -> referenced by activity_event
- setup_step -> referenced by setup_step_progress

## 2. Table Definitions

All `id` columns are `UUID NOT NULL DEFAULT gen_random_uuid()` with `PRIMARY KEY`; all `created_at` / `updated_at` columns are `TIMESTAMPTZ NOT NULL DEFAULT now()` (`updated_at` set on every write by the ORM `$onUpdate` hook). Both are restated in each table for completeness. Tables at 20 columns (`pro_account`, `booking`) are at the anti-pattern limit; any future column there requires a vertical split first.

## 4. Data Lifecycle & Integrity Decisions

Evidence key: **D/A** = the Delete/Archive cell of the named feature's Entity-Lifecycle Coverage Matrix (feature-overview.md); **Contention** = the entity's Contention line in feature-dependency-map.md; **Sensitivity** = its Data Sensitivity line; **S11** = technical-architecture.md Section 11 role/permission mapping (Pro = Full; Client = Own-only through an access link with no user account; Support = View-only, never writes); **XBR-21** = the append-only activity record. Version columns compare-and-set with `UPDATE ... WHERE id = :id AND version = :expected`.

**Audit-column decision, applied once and cited per row.** `created_by` / `updated_by` are FKs to `user`. Only one role that has a `user` row ever writes (the Pro; Support is View-only, S11), and Clients, who also write several entities, have no user account (S11). Where a Client or the system also modifies an entity, accountability is carried by the immutable Activity Event with its `actor_type` (XBR-21, FEAT-16.SPEC-005), which records Client and system actors that a `user` FK cannot. So no entity gets `created_by` / `updated_by`; each row states which of the two facts applies.

**Multi-tenancy:** Shared schema with the tenant key `pro_account_id` on every Pro-owned table (row-level isolation), and no separate `tenant_id` column. Evidence: every Stage 3 entity descends from one Pro Account and "no record is ever shared between two Pro Accounts" (feature-dependency-map.md, Pro Account Relationships); a client's data is "never visible to any other pro or client" (BRIEF.md Constraints; SC-03, SC-04); technical-architecture.md Section 10 ("Tenant scoping" with `withProScope(proAccountId)`) and Section 11 (RLS keyed on `pro_account_id`). The organization/team/workspace pattern is NOT activated: the product is strictly single-operator (SC-01; Access Matrix has no organization-scoped role), so each Pro Account is the isolation unit and there is no organization layer above it. Schema-per-tenant and database-per-tenant were rejected: a few hundred to low thousands of Pros with small per-Pro data (ASMP-22) do not justify per-tenant schemas, and cross-Pro platform work (subscription billing, support lookup, webhook routing) needs one schema.

## 5. Security & Access Model

**Enforcement model:** Row-level security (RLS) is the primary authorization mechanism at the data layer. The selected database (Supabase Postgres, technical-architecture.md Section 3 / ADR-003) supports it, and Section 11's role mapping already names "Postgres RLS policies on `pro_account_id`" and a "RLS client policy" as enforcement points. The application enforces the same boundary one layer up: `withProScope(proAccountId, fn)` opens a transaction and sets the transaction-local settings `app.actor_role` (`pro` | `client` | `support` | `system`), `app.pro_account_id`, `app.client_id` and `app.user_id` via `set_config`; policies read these with `current_setting(..., true)`. Support runs on a separate connection as a Postgres role with `SELECT`-only grants and column-masked views, so no write path exists structurally (Section 11, Support row). The `system` actor is the server-side service role used by webhooks, the job runner and the public booking flow after it resolves a handle; it bypasses no policy except where noted.

Role model (from Section 11, not invented here): **Pro** (`user.role = 'pro'`, Full on most capability groups), **Client** (Own-only, no user account, `app.client_id` from a redeemed access link), **Platform Operator (Support)** (`user.role = 'support'`, View-only for one Pro at a time via the open `support_session`).

Tenant scoping: every Pro-role and Client-role policy below is additionally `pro_account_id = current_setting('app.pro_account_id')::uuid` (the Section 4 tenancy decision). It is stated once here and written as "tenant" in the sketches. The Support role's tenant predicate is `pro_account_id = (SELECT pro_account_id FROM support_session WHERE operator_user_id = current user AND ended_at IS NULL)`, written as "open support session" below.

Compliance flags tied to the Section 4 retention decisions: US texting-consent rules (ASMP-24) drive the `messaging_consent` evidence retention; client deletion on request (ASMP-23, XBR-19) drives the hard-delete-plus-de-identify pattern across `client`, `booking`, `message` and `activity_event`; account closure (XBR-20) drives the 30-day purge of `user`, `session`, `data_export` and the Pro Account's personal columns with retention of de-identified financial rows (SC-22).

### Growth-Tier Notes

- **Partition `activity_event` and `message` by month (`occurred_at` / `created_at`):** when either table passes tens of millions of rows. At roughly 9,000 bookings a week across all Pros (Section 2 of the architecture; ASMP-22), messages run about two per booking and activity events several per booking, so this is a multi-year horizon, but both tables are append-only and time-ordered.
- **Read replica for slot polling:** when the FEAT-03 spike shows burst polling (about 50 simultaneous viewers of one Pro's page, architecture Section 2) saturates the primary; the alternative named in ADR-013 is a per-Pro/service/day slot-list cache invalidated on any booking, hold or block write.
- **Materialized money-list read model:** when the money list for a Pro with multi-year history (FEAT-28.SPEC-005) exceeds the one-second responsiveness target (ASMP-21).
- **Move insights to precomputed monthly rollups:** when a Pro's daily aggregate range scan for a Year period (FEAT-25.SPEC-002) stops being a bounded sum of at most 366 rows (it is today, so no action is needed at launch).
- **Purge tuning for `webhook_event` and `outbox_event`:** when their combined size becomes noticeable against the Supabase Pro 8 GB included storage (technology landscape note in ADR-003); shorten the retention window or partition by day.

## 9. Anti-Pattern Validation

| # | Check | Result | Notes |
|---|-------|--------|-------|
| 1 | Every table has a primary key | PASS | All 41 tables define `id UUID` as the primary key, including the 3 lookup tables (`code` is a UNIQUE FK target) |
| 2 | Every relationship has a FK constraint | PASS | All 68 relationships in Section 3 are declared FKs, with explicit ON DELETE and ON UPDATE. The one deliberate non-FK identifier, `verification.identifier`, is not a relationship (it must not disclose whether a contact exists, XBR-29). Cross-table rules that cannot be declared constraints (time-block-versus-booking overlap, handle-versus-forwarded-name uniqueness) are transaction-level checks documented in Sections 1 and 2 |
| 3 | Column types match data semantics | PASS | UUID ids, TIMESTAMPTZ instants, DATE for calendar days, TSTZRANGE for slots and busy time, JSONB only for the flexible activity `details`, webhook and outbox payloads, CHECK-constrained VARCHAR for enums, no VARCHAR-for-everything columns |
| 4 | Monetary values use DECIMAL (not INTEGER/FLOAT) | PASS | `price`, `deposit_value` (fixed), `price_agreed`, `deposit_amount`, `amount`, `processor_fee`, `tip_amount`, `deposits_collected`, `saved_from_no_shows` and subscription `price` are `DECIMAL(10,2)`; percentage `deposit_value` shares the column and is bounded 1-100 by CHECK |
| 5 | No comma-separated value columns | PASS | Every plural field (devices, weekly windows, busy periods, occurrences, previous link names, setup steps, per-service tallies) is a child table; see Section 6 |
| 6 | FK columns are indexed | PASS | Every FK column has an index or is the leading column of a composite / unique / GiST index; see the Indexes lists in Section 2 (Postgres does not create these automatically) |
| 7 | Timestamps include timezone | PASS | All timestamp columns are `TIMESTAMPTZ`; wall-clock rules use the Pro's IANA `timezone`, and the only non-instant time fields are the `DATE` calendar-day columns and the minute-of-day `SMALLINT`s on availability windows and recurrence patterns, both interpreted in the Pro's timezone |
| 8 | No unconstrained polymorphic associations | PASS | No `parent_type` + `parent_id` pairs. `message` and `activity_event` use an always-present `pro_account_id` plus one nullable `booking_id` (exclusive belongs-to) with CHECK constraints |
| 9 | No god tables (>20 columns) | PASS | Widest tables are `pro_account` and `booking` at exactly 20 columns (at the limit, flagged in Section 2); every other table has 19 or fewer. Vertical splits already applied (`booking_termination`, `slot_hold`) |
